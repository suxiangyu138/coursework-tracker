## 2. 课程技术点实现映射

| 知识点 | 具体实现 | 说明 | 答辩可指出 |
| --- | --- | --- | --- |
| `LocalDateTime` / `Duration` | `TimeUtils.countdown(now, dueAt)`；`Duration.between` 计算剩余 | 不用 `Date`/`Calendar` 等过时 API | 倒计时格式化与逾期判定 |
| `DateTimeFormatter` | `yyyy-MM-dd HH:mm` 解析与展示 | 线程安全，静态常量复用 | 输入校验、表格显示 |
| `Clock` 注入 | `ClockProvider` 持有 `Clock`，测试用 `Clock.fixed` | 避免业务代码直接 `now()` | 单测如何模拟"逾期" |
| 时区 | 统一本地时区语义，DB 存本地时间字符串 | 课程截止日本质是墙钟时间 | 为什么不用 UTC / 时间戳 |
| 枚举 + 状态机 | `AssignmentStatus`（TODO/DOING/DONE/SUBMITTED）+ 流转校验 | 带中文显示名、`isCompleted()` | 状态切换与非法流转 |
| `record` 不可变模型 | `Assignment`、`Course`、`Countdown`、`CourseGrade` | Java 16+ 语法，减少样板代码 | 为什么模型不可变 |
| 集合与 Stream | 分组 `groupingBy`、`toMap`、排序、`Optional` | 统计与聚合 | 按课程统计一行代码 |
| `Comparator` 链式排序 | `thenComparing` 多级排序、`reversed` | 紧急度 → 截止 → 权重 → id | 排序稳定性设计 |
| 泛型与接口 | `Dao<T>` 风格、`GradeScale` 接口、`ReminderSink` | 面向接口，便于测试与替换 | 接口隔离的好处 |
| 异常体系 | `BusinessException`、`DataAccessException` | 检查异常包装、保留 cause | 用户提示与日志分离 |
| JDBC | `Database` 单连接、`PreparedStatement`、事务模板 | 参数化防注入、`try-with-resources` | 事务边界在哪 |
| SQL | 建表、索引、外键级联、`UNIQUE`、`INSERT OR IGNORE` | 唯一约束做提醒去重兜底 | 为什么用唯一约束 |
| 多线程 | `ScheduledExecutorService`（守护线程）+ `javax.swing.Timer` | 后台扫描不碰 UI，`invokeLater` 回 EDT | 线程模型与竞态规避 |
| 线程安全 | 缓存快照不可变；DB 单连接同步访问 | 读写分离思路 | 为什么每秒不查库 |
| 文件 IO | `Paths`/`Files`、`FileLock` 单实例、日志滚动 | `try-with-resources` + `StandardOpenOption` | 单实例怎么实现 |
| `BigDecimal` | 成绩与权重计算 | 避免浮点误差，`HALF_UP` 保留 2 位 | 0.1+0.2 的坑 |
| Swing | `JTable` 自定义渲染器、`TableRowSorter`、`GridBagLayout`、`JDialog` | 自绘倒计时徽章、紧急度条 | 自定义渲染器怎么工作 |
| 事件模型 | 自写 `EventBus` + `SwingUtilities.invokeLater` | 数据变更 → 界面刷新解耦 | 为什么不用双写 |
| JFreeChart | `CategoryDataset` + `ChartPanel` | 主题配色、事件驱动刷新 | 图表数据从哪来 |
| 日志 | JUL + `FileHandler` | 分级记录、单文件 5 MB 上限 | 出问题怎么查 |
| 单元测试 | JUnit 5 参数化测试、`@TempDir` 集成测试 | 68 条用例，覆盖边界 | 覆盖率截图 |
| 构建 | Maven + Shade 打 fat jar | `--release 17` 跨版本兼容 | 打包产物怎么运行 |
| 系统集成 | `SystemTray`、注册表 Run 键（P2） | 托盘不可用时降级 | 桌面常驻怎么做的 |

## 3. 项目亮点（为什么这不是一个普通 CRUD）

### 3.1 紧急度不是拍脑袋，而是可解释的评分

大多数同类作业只做"按截止时间排序"。本项目把**剩余时间、作业权重、预计耗时**三个维度归一化后加权，输出一个可解释的分数：

```text
urgency = 0.55 × 时间压力 + 0.30 × 权重压力 + 0.15 × 工作量压力
```

界面上悬浮即可看到三个分量，用户能理解"为什么它排第一"。权重可通过设置调整，公式有 14 条单元测试覆盖边界（逾期封顶、权重夹取、耗时缺省、同分排序）。

### 3.2 倒计时 + 提醒 + 统计 + 成绩，形成闭环

| 单点功能 | 普通作业 | 本项目 |
| --- | --- | --- |
| 截止时间 | 存下来、显示 | 秒级倒计时 + 颜色分级 + 四档提醒 |
| 完成状态 | 打勾 | 权重完成度（防"小作业刷进度"）+ 剩余工作量 |
| 成绩 | 无 | 加权得分 + 总评预测 + 目标分反推 + GPA |
| 形态 | 打开才看 | 托盘常驻 + 单实例 + 断网可用 |

四件事共享同一份数据，改一条作业，排序、统计、图表、成绩预估同时更新。

### 3.3 工程化程度高于课程作业平均水平

- **分层**：UI / Service / DAO 依赖单向，算法层不出现 Swing 类型；
- **可测试**：时间源注入、纯函数算法、临时库集成测试；
- **可运维**：日志滚动、未捕获异常兜底、数据自动备份、数据库迁移框架；
- **可解释**：成绩预估显示公式与假设（"仅录入 60% 权重""剩余需 94.1 分"），而不是一个黑盒数字。

### 3.4 吃自己的狗粮

开发期间用这个工具管理课程设计本身的 7 个里程碑任务——自己每天用它，才知道哪里难用。这个使用过程本身就是最好的需求验证，也是答辩时最有说服力的故事。

### 4.2 预设问答

**Q1：为什么用 Swing 而不是 JavaFX？**

> 三个原因：① 部署简单，Swing 只需 JDK，单个 fat jar 双击即跑，JavaFX 要处理模块路径和额外打包；② 系统托盘是 JavaFX 的短板，`SystemTray` 是 AWT 的，混用要额外桥接；③ 课程环境（机房电脑）装 JDK 即可运行，风险最低。Swing 的观感问题用 FlatLaf 解决，深色主题和现代控件都有。

**Q2：紧急度的 0.55/0.30/0.15 是怎么定的？有依据吗？**

> 先验设定 + 样例校准。时间最刚性（过期直接 0 分），给最高权重；权重代表丢分多少，其次；预计耗时代表"要不要现在动手"，作为微调。用 5 条典型作业做校准，结果与人工判断一致。参数放在设置里可调，并保证三者之和为 1，便于用户按自己习惯调整。这也是把它做成"评分"而不是"硬规则"的原因——不同人的优先级感受不同。

**Q3：提醒会不会重复？程序没开的时候怎么办？**

> 三层去重：内存已提醒集合、`reminder_log` 表、数据库 `UNIQUE(assignment_id, rule_code)` 约束，写入用 `INSERT OR IGNORE`。程序没开时，提醒不会丢——启动后第一轮扫描会发现"应提醒但未提醒"的记录并补发，且同一规则只补一次。如果处于静音时段，提醒只进内存队列不落库，恢复后合并播报，避免"落库了但没弹窗"导致永久丢失。

**Q4：成绩预估凭什么准？权重没录满怎么算？**

> 不是"预测未来"，是"按当前假设推算"：已出分部分用实际分，未出分部分默认按已完成部分的加权均分。公式和假设直接显示在界面上（例如"仅录入 60% 权重，按 100 分制推算"）。目标反推是解一个一元一次不等式，`need = (100T − earned) / (100 − earnedW)`；`need > 100` 时明确告诉用户"即使剩余全满分最高 X 分"，不给出误导性结果。计算用 `BigDecimal`，避免浮点误差。

**Q5：为什么用 SQLite，不直接存 JSON？**

> 三个需求 JSON 做不好：① 按截止时间范围查询（提醒扫描）；② 外键级联删除与唯一约束（去重兜底）；③ 事务（批量导入失败要回滚）。SQLite 单文件、免安装、可用 Navicat 直接打开检查，非常适合桌面小工具。同时 DAO 层做了隔离，真出问题可以换 H2。

**Q6：后台线程会不会和界面线程冲突？**

> 分工明确：所有 Swing 操作只在 EDT；调度线程只做"查数据 + 算 + 发事件"，通过 `SwingUtilities.invokeLater` 回到 EDT 更新界面。界面每秒刷新只读内存快照，不查数据库，避免 IO 阻塞 EDT。数据库用单连接 + 同步访问，写入路径短（毫秒级），也避免了并发写的锁问题。代价是批量导入需要 `SwingWorker`，这点在文档里写明了。

**Q7：数据丢了怎么办？**

> 四道防线：SQLite WAL 模式（崩溃可恢复）、写操作事务、每日自动备份（保留 7 份）、手动导出 JSON。强杀进程的测试用例（TC-E-10）验证过重启后数据完整。另外程序启动时会检查数据库可写性，只读或损坏时给出明确提示而不是静默失败。

**Q8：如果数据量到 10 万条还撑得住吗？**

> 当前设计面向单学期几千条，绰绰有余。到 10 万条需要三处改造：提醒扫描加时间窗索引（已有 `idx_assignment_due`）、表格分页或虚拟列表、统计结果缓存。DAO 接口不变，属于可演进的设计；但这不是本项目的目标场景，文档里也写明了范围。

**Q9：和手机上的待办 App 比，优势在哪？**

> 不是替代，是补位：待办 App 记录"要做什么"，但不知道"占多少权重、算多少分、还差多少到目标绩点"。本项目把课程维度（学分、权重、成绩）和作业维度打通，这是通用待办工具做不到的。而且它常驻在写作业的电脑上，录入零成本、断网可用、数据不出本机。

**Q10：单元测试怎么做的？覆盖率多少？**

> 只对"算错很难发现"的纯函数做单测：时间格式化、紧急度、提醒规划、成绩计算、统计聚合，共 68 条用例，含参数化与边界（逾期、闰年、跨年、除零、不可达）。UI 用手工用例表（24 条）。覆盖率目标 80%，用 JaCoCo 出报告。数据库测试用 `@TempDir` 临时库，绝不碰真实数据。

## 7. 可能的扣分点与规避

| 常见扣分点 | 本项目规避方式 |
